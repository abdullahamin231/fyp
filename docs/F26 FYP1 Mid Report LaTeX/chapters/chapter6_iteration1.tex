\section{Evidence Graph Linking and Change Analysis (Mishal Fatima)}
\label{sec:impl-linking-analyser}

This part of the iteration fills the evidence graph from two directions. The
\emph{linker} connects a pull request to the Jira issues it explicitly names
(FR-04). The \emph{change analyser} works out what a pull request changed at
the level of functions and tests, and turns that into evidence the verifier
can cite (FR-06, FR-25). Both write into the tables of the ERD in
Figure~\ref{fig:erd} (\texttt{events}, \texttt{nodes}, \texttt{edges}), which
Abdullah implemented as Supabase migrations; both live in the worker
(\texttt{apps/\allowbreak{}worker}) beside his verification pipeline.

\subsection{Deterministic pull-request to issue linking}

\paragraph{Rule.} A link is created only from an explicit reference: a Jira key
such as \texttt{UNI-123} written in the pull request's title, branch name or a
commit message. Nothing is inferred from similar wording. A link created this
way is stored as \texttt{TRACKS}, \texttt{source\_class = observed},
confidence 1.0, resolver \texttt{explicit-reference}, which makes it eligible
to support a decisive finding under FR-05.

\paragraph{Finding the keys.} \texttt{extract-keys.ts} is a pure function with
no database access. Its pattern is:
{\small
\begin{verbatim}
(?<![A-Za-z0-9])([A-Z][A-Z0-9]+)-([1-9][0-9]*)(?![A-Za-z0-9])
\end{verbatim}
}
\noindent The two look-arounds stop a key being read out of a longer word
(\texttt{XUNI-1}, \texttt{UNI-12abc}); the project part must start with an
upper-case letter, as Jira requires; and the number cannot start with zero,
because Jira never issues one. Matching is case-sensitive on purpose:
accepting \texttt{uni-123} would also accept ordinary text such as
\texttt{covid-19}. Strings like \texttt{UTF-8}, \texttt{SHA-256} and
\texttt{ISO-8601} still match the pattern, so the workspace's list of Jira
project keys (here \texttt{UNI}) is applied as a second filter. Each key is
reported once, together with every place it appeared, and that list is kept
on the link as provenance.

\paragraph{Writing to the database.} The database steps run in one Postgres
function, \texttt{link\_\allowbreak{}pull\_\allowbreak{}request\_\allowbreak{}event} (migration 00015):
\begin{enumerate}
  \item insert the event; if this GitHub delivery id was seen before, the
        unique constraint on \texttt{events(source\_tool, vendor\_delivery\_id)}
        makes the insert a no-op and the function stops (``same event twice'');
  \item create or update the \texttt{PullRequest} node;
  \item if no key was found, stop: the event is still recorded, because
        \texttt{events} is a log;
  \item for each key, look up the \texttt{Ticket} node. If there is none, report
        \texttt{unknown\_key} and do not invent a node; the key stays in
        \texttt{events.references} so it can be resolved later. Otherwise
        insert the \texttt{TRACKS} edge.
\end{enumerate}
These steps are in SQL rather than TypeScript for one reason: they must
succeed or fail together, and the Supabase client sends every call as its own
transaction. A function always runs as one transaction, so an event can never
be recorded without its links. The function is callable only with the
worker's service-role key, because it bypasses row-level security.

\paragraph{Duplicate links.} Migration 00010 (Abdullah's) allows one current
edge per \texttt{(from, to, type)} through a partial unique index with the
condition \texttt{link\_\allowbreak{}state <> 'revoked'}. The insert names the same
condition in its \texttt{ON CONFLICT} clause. Postgres only accepts that clause
when the condition matches the index exactly, and my first version used a
different one, \texttt{valid\_\allowbreak{}to is null}, and the tests failed against the real
migration with ``no unique or exclusion constraint matching the ON CONFLICT
specification''. With the matching condition, a second mention of an existing
link adds nothing, a link a reviewer dismissed stays dismissed, and a revoked
link can be created again.

\begin{longtable}{>{\raggedright\arraybackslash}p{0.24\textwidth} >{\raggedright\arraybackslash}p{0.33\textwidth} >{\raggedright\arraybackslash}p{0.33\textwidth}}
\caption{Linker outcomes and what decides each.}\label{tab:linker-outcomes}\\
\hline\textbf{Case} & \textbf{Outcome} & \textbf{Decided by} \\
\hline\endfirsthead
\hline\textbf{Case} & \textbf{Outcome} & \textbf{Decided by} \\
\hline\endhead
Key found, ticket exists & \texttt{linked}: new \texttt{TRACKS} edge & edge insert (step 4) \\
No key & \texttt{no\_key}: event kept, no edge & step 3 \\
Key found, no ticket & \texttt{unknown\_key}: no edge, no invented node & ticket lookup (step 4) \\

\hline\end{longtable}

\subsection{Change analyser}

\paragraph{Input and output.} The analyser takes a git repository and two
commits, base and head. It reads only git's stored objects
(\texttt{git diff}, \texttt{git show}, \texttt{git grep} at a commit), never a
checked-out folder, and never runs the repository's code unless asked to
(below). The same two commits therefore always give the same output. It
reports the changed files and hunks, the changed symbols, a bounded caller
neighbourhood, the related tests, and dynamic code it cannot follow.

\paragraph{From changed lines to changed symbols.} \texttt{git diff -U0} gives
each hunk's exact line ranges on both sides. Every file involved is parsed with
the TypeScript compiler's own parser (syntax only), which lists every function,
method, class and function-valued variable at any depth. Nested definitions
matter: in react-hook-form, \texttt{clearErrors} is an arrow function declared
inside \texttt{createFormControl}, and that inner function is what a fix
changes, so it is named \texttt{createFormControl.clearErrors}. Each changed
line is then mapped to the \emph{innermost} symbol around it: the one with the
smallest range that still contains the line. Added and modified lines are
looked up in the head version, removed lines in the base version. A symbol
found at head but not at base is \emph{added}; one found at base but not at
head is \emph{deleted}; one found in both is \emph{modified}. Lines outside any
symbol, such as imports or re-exports, are reported as module-level changes
rather than forced onto a symbol.

\paragraph{Neighbourhood and tests.} For each changed symbol the analyser
searches the head commit for call sites, keeping at most 40 files and 10
callers. A call counts as a caller only when it is in the same file, or in a
file whose relative import resolves to the symbol's file. Calls that only
share the name are counted but not trusted. Test evidence is collected the
same way: test blocks (\texttt{it}/\texttt{test}) that the diff touches, and
test blocks elsewhere that mention a changed symbol. A \texttt{COVERS} edge
from a test to a symbol is created only when the test file imports the
symbol's file; a test that merely mentions the name is kept as evidence
without an edge. Calls whose target cannot be known statically (a dynamic
\texttt{import(x)}, \texttt{require(x)}, \texttt{obj[x]()}) are listed as
\emph{unresolved} and never turned into edges.

\paragraph{Symbol cards (FR-25).} Each changed symbol becomes a card with
fixed fields in a fixed order, so the same symbol always gives the same bytes
and the verifier's citation check can compare hashes. Abridged real card from
pilot case P01 (imports shortened; the commit subject's emoji removed):
{\small
\begin{verbatim}
symbol: createFormControl.clearErrors (function, modified)
file: src/logic/createFormControl.ts lines 1562-1582
path tokens: src logic create form control ts
signature: const clearErrors: UseFormClearErrors<TFieldValues> = (name) =>
doc: (none)
comments: (none)
imports: ../constants, ../types, ../utils/cloneObject, ... (51 in total)
callers: createFormControl.validateForm (same-file, lines 768, 791);
         useForm (src/useForm.ts:144, import)
unresolved: (none)
coverage: 8/11 lines run by tests; changed lines 1/1
commit: fix #13790: setError and clearErrors produce a new errors reference
---
const clearErrors: UseFormClearErrors<TFieldValues> = (name) => { ...
\end{verbatim}
}
\noindent The card, the diff hunks and the test blocks are written to the
graph as \texttt{CodeSymbol}, \texttt{Commit} and \texttt{TestCase} nodes
carrying \texttt{payload.slotItems}, the exact shape Abdullah's packet builder
already reads, so no change was needed on his side to consume them.

\paragraph{Python.} Python files go through a second parser that uses
Python's own block rule: a definition ends before the next line indented at or
left of its \texttt{def} or \texttt{class}. Lines inside triple-quoted strings
or open brackets are skipped when looking for that line, so a docstring or a
multi-line call does not end a function early. This is simpler than a full
grammar and easy to check by hand. The trade-off is stated: functions created
with \texttt{exec} or classes built with \texttt{type(...)} are not seen.

\paragraph{Test runs and coverage (opt-in).} Running a repository's tests
means executing its code, so it happens only when a command is given. The
command runs in a temporary copy of the head commit, with a time limit, and
the copy is deleted afterwards. If the command writes an LCOV coverage report
(Jest, Vitest and coverage.py all can), each symbol card records how many of
its lines, and how many of its \emph{changed} lines, the tests ran.

\paragraph{Publishing.} The nodes and edges are written by a second database
function, \texttt{publish\_\allowbreak{}analysis} (migration 00016), in one transaction.
Nodes are updated in place when the same change is analysed again, and an edge
whose other end is not yet in the graph (for example, a pull request not yet
ingested) is reported as skipped, never invented.

\subsection{Limitations}
\begin{itemize}
  \item No GitHub webhook endpoint yet: the linker has run on the hosted
        database only with scripted demo events.
  \item JSON and other configuration files are not parsed into symbols (the
        P06-S3 miss).
  \item Only relative imports are resolved when deciding callers and
        \texttt{COVERS} edges; imports through package names (common in
        monorepos such as Mantine) fall back to name-only matches, which are
        counted but not trusted.
  \item The Python parser has been tested on synthetic repositories only; all
        pilot cases are TypeScript.
  \item The packet builder originally walked two hops from a criterion, which
        did not reach the \texttt{CodeSymbol} and \texttt{TestCase} nodes the
        analyser writes. Abdullah raised the bound to three hops on 11 October,
        so they are now reached. The hand-off is tested end to end on the
        production provider and packet builder, but not yet in a live run
        against Supabase.
\end{itemize}

\section{Source Ingestion and Event Reliability (Haaniah Ismail)}
\label{sec:impl-ingestion}

This part of the iteration is everything between an external tool and the
evidence graph. Three read-only adapters turn vendor notifications into one
normalised form (FR-01); a reliability layer guarantees that the graph reaches
the same final state whether an event arrives once, twice, late or not at all
(FR-02, FR-16); and three deterministic rules read the resulting state to raise
findings without any model involvement (FR-12). All of it lives in
\texttt{apps/web/src/lib/integrations} and
\texttt{packages/contracts/src/ingestion.ts}; it writes through the tables
Abdullah implemented as
migrations, which Mishal's linker and analyser then read from
(Section~\ref{sec:impl-linking-analyser}).

The design question this part answers is not how to call three APIs. It is how
to build a dependable record of what happened out of three services that
version their data on independent clocks, deliver notifications on a
best-effort basis, and occasionally do not deliver them at all.

\subsection{The normalised event envelope}

Every adapter produces the same record, defined once in
\texttt{packages/\allowbreak{}contracts} so that the database, the tests, the
diagrams and this chapter cannot drift apart. Four of its fields carry the
reliability guarantees and are worth stating individually.

\begin{longtable}{>{\raggedright\arraybackslash}p{0.26\textwidth} >{\raggedright\arraybackslash}p{0.64\textwidth}}
\caption{Envelope fields that the reliability layer depends on.}\label{tab:envelope-fields}\\
\hline\textbf{Field} & \textbf{What it decides} \\
\hline\endfirsthead
\hline\textbf{Field} & \textbf{What it decides} \\
\hline\endhead
\texttt{event\_id}, \texttt{vendor\_delivery\_id} & Whether this delivery has
  been seen before. Derived from vendor data, never generated, so a
  re-delivery produces the same identifier. \\
\texttt{entity\_id}, \texttt{version} & Whether this event is newer than what
  the graph already holds. This is what makes out-of-order delivery safe. \\
\texttt{occurred\_at} vs \texttt{received\_at} & Vendor delay separated from
  internal delay. Collapsing the two would make a slow vendor
  indistinguishable from a slow worker. \\
\texttt{references} & Explicit work-item keys and design URLs found in the
  payload, with the place each was found. This is the field Mishal's linker
  consumes. \\
\hline\end{longtable}

\noindent The raw payload is stored next to the envelope with a hash of its
bytes, because a finding cites evidence and that evidence must remain readable
after the source record changes.

\subsection{Source adapters}

\paragraph{One interface, three implementations.} Each adapter exposes
\texttt{verify}, \texttt{normalise} and \texttt{poll}. The interface is defined
by the \emph{role} a source plays --- design intent, work item, change --- not
by the product that currently fills it, so adding a fourth source is one
adapter written against the existing contract and changes no layer above it.

\paragraph{\texttt{normalise} is a pure function.} It takes a payload and
returns envelopes. No database, no clock, no environment. This is a deliberate
seam rather than a style preference: it is what lets the same function be
driven by a live webhook and by a recorded payload from the replay harness, so
the harness tests the production code path rather than a parallel one. It also
means a payload that maps to nothing returns an empty list rather than throwing,
because the vendor must still receive a success response or it will retry.

\paragraph{Verification differs by vendor, and the difference bites.}
GitHub signs with an HMAC-SHA256 digest of the request body in
\texttt{X-Hub-\allowbreak{}Signature-256}. Jira signs with the same algorithm
but names the header \texttt{X-Hub-\allowbreak{}Signature}, without the suffix.
Both digests are computed over the \emph{raw} bytes of the body: a payload that
has been parsed into an object and re-serialised produces a different digest
even though it represents the same data, and the failure is silent --- the
signature simply does not match, with nothing in the payload to indicate why.
Verification therefore runs on the raw buffer before any parsing, in all three
adapters.
The implementation consequence is that signature verification is a separate
boundary from parsing: malformed JSON cannot be treated as an authenticated
event, and a re-serialized object cannot be substituted for the signed bytes.

\paragraph{Event selection, and what is deliberately ignored.} Figma publishes
seven webhook event types. Two are used: \texttt{FILE\_VERSION\_UPDATE}, sent
when a user creates a named version, and
\texttt{DEV\_MODE\_STATUS\_UPDATE}, sent when the development status of a layer
changes. The general \texttt{FILE\_UPDATE} event is deliberately not used as a
drift trigger: it fires only after a period of editing inactivity, so it is
both delayed and too coarse to attribute to a particular design decision. This
is why design intent is versioned in the graph at named-version granularity ---
that is the finest granularity the source actually reports.

\paragraph{Reference extraction.} Work-item keys are read from a pull request's
title, body, branch name and commit messages; design URLs and development
resources are read from work-item descriptions. Extraction is string matching
only --- nothing is inferred from similar wording --- and every candidate is
recorded together with where it was found, because a key in a branch name and a
key in a comment do not carry the same confidence. Filtering and ranking are
not done here; they belong to the linker, which decides what becomes an edge.

\subsection{Reliability: three mechanisms, not one}

The most common way to get this wrong is to assume a queue with retries covers
it. It does not, and the reason is worth stating precisely: a queue can only
replay what was delivered. An event a vendor never sent will never be retried,
and nothing in the receiving system knows it is missing. Three distinct
mechanisms are therefore implemented.

\begin{longtable}{>{\raggedright\arraybackslash}p{0.20\textwidth} >{\raggedright\arraybackslash}p{0.34\textwidth} >{\raggedright\arraybackslash}p{0.36\textwidth}}
\caption{The three reliability mechanisms and the failure each addresses.}\label{tab:reliability-mechanisms}\\
\hline\textbf{Mechanism} & \textbf{Failure it addresses} & \textbf{How} \\
\hline\endfirsthead
\hline\textbf{Mechanism} & \textbf{Failure it addresses} & \textbf{How} \\
\hline\endhead
Idempotency & The same event delivered twice & The identifier is checked before
  processing; a repeat is a no-op and the graph is not touched \\
Checkpointing & Not knowing what was missed & A marker per connected resource
  records the last event processed and when \\
Reconciliation & An event the vendor never sent & The adapter polls, compares
  against the checkpoint, and synthesises the missing event into the normal
  pipeline \\
\hline\end{longtable}

\paragraph{Step order is the guarantee.} Processing follows a fixed order: the
raw payload and envelope are persisted \emph{before} any evaluation, and the
checkpoint advances \emph{last}. The consequence is that a crash mid-way causes
re-processing rather than loss, and re-processing is safe because the duplicate
branch is a no-op. Reversing either end of that order would break it: advancing
the checkpoint first would silently lose the event, and evaluating before
persisting would produce findings that cite evidence the system never stored.

\paragraph{Three different outcomes that all mean ``nothing happened''.} A
rejected event failed verification and was never trusted. A discarded event was
already applied once. An ignored event was superseded by a newer version. These
are counted separately rather than collapsed, because collapsing them would
hide a real failure --- a rising rejection rate means a secret has rotated,
while a rising duplicate rate is normal vendor behaviour.

\paragraph{Stale sources (FR-16).} When a source cannot be reached beyond a
configured threshold, its connected resources are marked
\texttt{SOURCE\_\allowbreak{}STALE} and every finding that depends on them is
downgraded rather than computed from data that may no longer be current. The
reviewer is told the system cannot establish current state. The alternative ---
serving an old verdict as though it were current --- is the failure this
project exists to prevent, so it is not available even as a fallback.

\paragraph{Vendor delivery semantics differ, and the design accounts for it.}
Jira's delivery is documented as best-effort: roughly five retries with
exponential back-off over about thirty minutes, after which the event is lost,
with no dead-letter queue. Its connection and response timeouts are fixed at
five and twenty seconds, which is why the receiver persists and enqueues rather
than doing any analysis inside the request. Ordering is not guaranteed under
concurrency. Each of these is a reason the reconciliation path is not optional:
webhooks are treated as an optimisation over polling, never as the mechanism of
record.

\subsection{Deterministic rules as versioned records}

Rules 1--3 are stored as declarative records rather than written as code in a
handler, each carrying an identifier and version, the edge type it attaches to,
its trigger, its guards, a grace period, what it produces, whom it notifies and
the resolution actions it offers. Two consequences follow. A finding records
which \emph{version} of a rule produced it, so a finding raised last month can
still be explained after the rule changes. And a rule can be re-parameterised
for a team whose workflow differs without editing and redeploying code.

Guards matter as much as triggers. Rule~1 does not fire on a cosmetic design
edit; Rule~2 does not fire when the ticket sits in a workflow state the team
has mapped as an acceptable post-merge state. Without guards both rules would
be technically correct and practically useless, because the finding that is
always raised is the finding that is always dismissed.

\subsection{The replay harness, kept permanently}

The mock vendor is not scaffolding awaiting removal. It is the conformance
harness every adapter passes before it is given live credentials, and it is
retained for a reason that does not expire: duplicate delivery, out-of-order
arrival, an undelivered webhook and a prolonged outage cannot be produced on
demand against a live service. The scenarios behind every reliability claim in
this project are only testable through replay.

It runs in two modes. In \emph{envelope} mode it emits envelopes directly into
the reliability layer, which tests that layer in isolation and is how a new
integration is exercised before its adapter exists. In \emph{payload} mode it
replays recorded vendor payloads through the real \texttt{normalise}, which
tests normalisation and reliability together on the production code path. Which
driver feeds the pipeline is an environment setting; no adapter contains a
branch on whether it is being tested.

\subsection{Demonstration evidence}

\paragraph{Reliability scenarios.} The controlled scenarios are implemented in
the ingestion contract tests and replay harness. A fresh execution output was
not committed at the reporting date, so this report does not claim a numeric

\texttt{SOURCE\_STALE} followed by recovery.

\paragraph{Rules firing on live data.} Rules~1--3 are implemented as versioned

\paragraph{Tests.} The four reliability properties this design rests on are

\texttt{packages/contracts/test/ingestion.test.ts}, which drives the

\subsection{Limitations}
\begin{itemize}
  \item All three adapters are implemented, but the committed evidence is
        currently code and documented fixtures rather than a reproducible
        live-provider run.
  \item Figma reports design intent only at named-version granularity. A change
        made without creating a named version is invisible to Rule~1 until a
        version is cut or reconciliation polls the file.
  \item Jira's delivery is best-effort with no dead-letter queue, so an event
        lost after its retries are exhausted is recovered only at the next
        reconciliation poll, not immediately. The gap is bounded by the polling
        interval; no measured interval is claimed here.
  \item No provider rate-limit measurement is claimed because live traffic was
        not captured in the repository evidence.
  \item Duplicate, out-of-order, outage and missing-webhook scenarios remain
        replay-only by design, because they cannot be induced reliably against
        a live vendor.
\end{itemize}

\section{Verification Pipeline and Reviewer Surface (Abdullah Amin)}
\label{sec:impl-verification}

The verification module addresses the central iteration question: how can a
finding be checked against bounded evidence without allowing an ungrounded
model response to become a system fact? Abdullah's implementation separates
evidence assembly, model interaction and verdict admission. The worker builds
an immutable context packet, runs a bounded verifier loop, passes the result
through a pure provenance gate, and persists both the result and the evidence
needed for a reviewer to reconstruct it. This is the implemented verification
slice, rather than a claim of general program correctness.

\subsection{Completed features and module boundary}

The completed module contains four connected parts:

\begin{enumerate}
  \item deterministic context-packet construction from graph evidence, diffs,
        symbol cards and test evidence;
  \item a bounded verifier loop with scope, verification and conditional critic
        passes;
  \item a verdict/provenance gate that can reject or downgrade model output but
        cannot promote an unsupported status; and
  \item persistence and reviewer-facing finding creation for verdicts that need
        human attention.
\end{enumerate}

The implementation is integrated into the worker and shared contracts rather
than being an isolated demonstration. The principal artefacts are
\texttt{apps/worker/src/packet/assemble.ts},
\texttt{apps/worker/src/packet/builder.ts},

and gate failures create review findings.

\subsection{Technical implementation details}

\paragraph{Deterministic packet builder.}
\texttt{assemble} fills the packet slots in a fixed order and admits evidence
in provider order. Each slot has an explicit token budget. The first item that
would exceed a slot budget causes the remaining items in that slot to be
recorded as \texttt{BUDGET\_EXCEEDED}; if the total budget is still exceeded,
whole slots are evicted in a fixed eviction order. No item disappears silently:
the manifest records every omitted item and its reason. Duplicate citation
handles throw an error because they would make a later citation ambiguous.

\texttt{buildPacket} then hashes the canonical manifest as \texttt{packetHash},
hashes the packet template contract as \texttt{promptHash}, and renders a
byte-stable packet body. The content hash map is retained so the gate can
check that a cited span is both present in the packet and identical to the
content shown to the verifier.

\paragraph{Bounded verifier loop.}
\texttt{runVerifierLoop} records a pass record for every model interaction,
including the prompt hash, packet references, parse result, stop reason,
model metadata and duration. Pass one checks whether the packet contains
applicable evidence. If it does not, the loop abstains with
\texttt{NO\_APPLICABLE\_EVIDENCE}. Pass two requests the evidence-backed
verdict. Pass three is conditional: it is used for a disputed finding, a
\texttt{PARTIAL} answer, or a decisive answer with weak citation support.
The critic is downgrade-only, so it cannot turn a weaker answer into a
\texttt{SUPPORTED} answer. The loop is bounded at three passes.

Malformed model output is not repaired into a success-shaped response. It is
recorded and handed to the gate for rejection. If the model is unavailable,
the loop returns an explicit \texttt{MODEL\_UNAVAILABLE} abstention. These
branches preserve the distinction between ``not verified'' and ``verified
as correct''.

\paragraph{Verdict and provenance gate.}
The pure \texttt{gate} function in
\texttt{packages/contracts/src/gate.ts} applies ordered checks: strict schema
validation, citation resolution, rule applicability, link eligibility,
freshness, confidence thresholds, hard gate 1, and provenance. A decisive
status with no evidence is rejected as an abstention. A citation that is not
in the packet, or whose content hash differs from the packet manifest, is
removed from the decisive evidence and causes a downgrade or rejection.
Freshness and link-policy failures likewise prevent an unsupported decisive
result. The gate records every check and its reason code so the reviewer sees
why a result passed, was downgraded, or was rejected.

\paragraph{Persistence and reviewer findings.}
The persistence layer inserts the packet, pass records and gated verdict as
append-only records. Re-verification creates a new packet/verdict pair rather
than overwriting the evidence behind an earlier decision. The finding helper
creates a review item when the verdict is not a clean supported result or
when the verdict explicitly requires review. A newer live finding supersedes
an older live finding for the same criterion, while a human-closed finding is
not silently reopened.

\subsection{Algorithms and technical decisions}

The main design decision was to make evidence admission and verdict admission
separate deterministic boundaries. The packet builder answers ``what was the
verifier shown?''; the gate answers ``what is allowed to become a stored
verdict?''. This prevents the model from selecting evidence outside the
immutable packet and makes a run reproducible from the packet manifest,
content hashes, pass records and model metadata.

The critic pass is conditional rather than unconditional to keep the verifier
bounded and to avoid presenting a second model call as independent proof. Its
role is to challenge weak or disputed evidence, and its only permitted effect
is to preserve or lower the pass-2 status. The system therefore treats a
missing model, malformed output, stale source or unresolved citation as an
explicit failure mode rather than silently substituting a positive answer.

The module also uses a type-system analyser to produce symbol-level evidence:
changed symbols, their qualified names and signatures, imports, callers,
documentation context and relevant tests. This makes the context packet
specific to the change under review instead of relying on a raw diff alone.
The worksheet records the analyser pilot as matching the labelled cases except
for one known miss, which remains a limitation rather than being hidden by a
fallback.

\subsection{Tools, frameworks and architecture evidence}

\subsection{Iteration outcome and limitations}

This contribution completes the deterministic verification slice for Iteration
1: a change can be converted into bounded evidence, checked through a
multi-pass verifier, admitted or downgraded by a pure gate, and exposed as a
review finding with provenance. The module is therefore ready for a live
evaluation: the analyser publishes evidence from a real repository into the
configured Supabase queue, and the verifier reads it back from the graph.

The result does not establish general correctness or eliminate human review.
The type-system analyser has a known miss in the pilot cases, and unresolved
type ambiguity can require fixture-backed or manual handling. The committed
evidence does not claim a production local-model latency or memory benchmark,
nor does it claim that every provider-backed dataset edge case has been
exercised live. Additional verifier edge cases and final evaluation
rehearsal remain planned work. These boundaries are consistent with the
worksheet's recorded next action: complete the final report, add verifier edge
case tests, and prepare the evaluation demonstration.

\section{Reproducing This Iteration}
\label{sec:ch6-repro}

The three modules above can be brought up and re-run from a clean machine.
Everything below was taken from the repository at the evaluation commit
\texttt{ce0ae2c} (12 October 2026); where a step could not be executed in the
reporting environment it is marked as such rather than described as done.

\subsection{Prerequisites}

\begin{itemize}
\item \textbf{Node.js 20 or later (LTS) with npm.} The repository is a single
  npm workspace root: \texttt{packages/contracts}, \texttt{apps/worker} and
  \texttt{apps/web} are the three workspaces listed in the root
  \texttt{package.json}.
\item \textbf{Git}, to check out the evaluation commit.
\item \textbf{PostgreSQL 15 or later}, or a hosted Supabase project. The
  committed database layer is plain SQL and does not depend on a Supabase-only
  feature for the linking, analyser or verifier paths; a local PostgreSQL
  instance is sufficient for the worker and contracts suites.
\item \textbf{Python 3.10 or later}, needed only by the change analyser's
  Python parser and the dataset agreement scripts. It is not needed for the
  TypeScript build.
\end{itemize}

No global tooling is required beyond these. There is no CI pipeline in the
repository yet (defect D-02), so the commands below are the whole procedure.

\subsection{Install}

\begin{verbatim}
git clone https://github.com/abdullahamin231/fyp.git
cd fyp
npm install
\end{verbatim}

\texttt{npm install} at the root installs all three workspaces and then runs
the root \texttt{postinstall} hook, which builds \texttt{@unify/contracts}.
That build must succeed before the worker or web app can be compiled, because
both import the generated contract types; the \texttt{prebuild} and
\texttt{pretest} hooks in each workspace rebuild it automatically, so a
contract change never needs a manual rebuild step.

\subsection{Database}

The schema is \texttt{supabase/migrations/} and is the source of truth: apply
the files in numeric order, \texttt{00001} through \texttt{00016}. They are
idempotent-by-construction (each creates or alters a named object) and are
meant to be applied to an empty database.

\begin{verbatim}
psql "$DATABASE_URL" -f supabase/migrations/00001_enums.sql
psql "$DATABASE_URL" -f supabase/migrations/00002_tenancy.sql
# ... through 00016_publish_analysis.sql
\end{verbatim}

\noindent The ordering matters in three places: \texttt{00003} needs the enum
types from \texttt{00001}; \texttt{00010} adds the partial unique index the
linker's duplicate safety depends on; and \texttt{00015} and \texttt{00016}
create the \texttt{link\_pull\_request\_event} and \texttt{publish\_analysis}
functions used by the linker and the analyser respectively. Running the
linking tests against a database missing \texttt{00010} fails on the
\texttt{ON CONFLICT} predicate rather than silently duplicating rows, which is
the behaviour the test suite was written to catch.
