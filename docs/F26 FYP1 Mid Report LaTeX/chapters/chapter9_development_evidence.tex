\section{Tools and Tool-Assisted Development}
\label{sec:ch9-genai}

\subsection*{Classification approach}

Generative tools were used during this project. Assistance is classified per
artefact rather than per member, because the same member used different levels
of assistance on different work. The four levels are those defined by the
evaluation instrument: \textbf{L1} supportive, covering formatting, phrasing
and minor debugging hints; \textbf{L2} assisted, where significant code, tests,
diagrams or report text were generated and then reviewed, modified and
integrated by the member; \textbf{L3} core assist, where a major module or
central feature was produced with substantial generative help; and \textbf{L4}
substituted, where generated work could not be independently explained or
modified by the member it is attributed to.

The project's position on L4 is that such work is not presented as
independently completed. This was applied in practice rather than stated in
principle, and the next subsection records the one occasion on which it was.

\subsection*{A correction made during the iteration}

Draft text for several report chapters was generated rather than written by the
members those chapters were assigned to. The drafts were reverted in commit
\texttt{7766cbc} and each chapter returned to its section skeleton for its
owner to write.

The reasoning was that a generated chapter cannot satisfy two separate
requirements at once: the anti-plagiarism declaration, and the requirement that
each member be able to locate, explain and modify the work attributed to them
under questioning. A chapter that reads well but that its named author cannot
defend is an L4 artefact presented as independent work, which the classification
above prohibits. Reverting cost the team approximately 1,560 lines of apparent
progress and several days of rewriting,
and it is recorded here rather than omitted because
the commit is visible in the repository and an unexplained reversion is worse
than a declared one.

\section{Security and Privacy Considerations}

\paragraph{Access is read-only throughout.} All three source integrations use
read-only, least-privilege scopes. The system never writes to a connected tool.
This is a design commitment rather than an unimplemented feature: there is no
write path to remove later.

\paragraph{Credentials.} Tokens are held by one component, encrypted at rest,
and supplied through environment configuration rather than committed. A
revocation path is documented. Webhook payloads are authenticated before they
are parsed, using the signature scheme each vendor specifies.

\paragraph{Artifact content does not leave the deployment.} All model inference
runs on team-operated infrastructure. Repository content, work-item text and
design metadata are not transmitted to a third-party model interface. This is
what makes the system usable by a team whose policy prevents sending source
code to an external service, and it is the reason the hosted-model option was
removed from the committed design.

\paragraph{Retained data.} Raw payloads are stored alongside their normalised
form because a finding cites evidence that must remain readable after the
source record changes. They contain vendor event data, issue/design/PR
metadata, references and hashes, but not OAuth access tokens, refresh tokens,
webhook secrets or encryption keys. The connection table stores secret-bearing
values only as encrypted ciphertext. A retained-payload secret scan remains a
release check and has not been reported as a measured result here.

\paragraph{Untrusted input.} Work-item text, commit messages and design
metadata are treated as data, never as instructions. The verifier does not act
on instructions embedded in artifact content, and its output is constrained to
a schema and validated against the evidence packet before it can influence
anything.

\paragraph{No individual performance measurement.} The system records who
resolved a finding and when, because a finding must be auditable. It does not
derive productivity measures about individuals, and the audit record exists to
make findings re-readable rather than to attribute performance.

\section{Current Limitations}

Stated as limitations of the project at the mid stage, not as future work.

\begin{itemize}
  \item \textbf{The evaluation set is small by construction.} No public dataset
        links a design artifact, a work item and a code change for the same
        unit of work, so the gold set is built by hand and is bounded by the
        labelling effort three people can sustain. Results are therefore
        reported as counts with intervals, and the set is positioned as a
        diagnostic instrument rather than a benchmark.
  \item \textbf{Code analysis is language-specific.} Extracting symbols,
        resolving imports and mapping tests requires a parser per language.
        Two language families are declared; configuration formats are not
        parsed into symbols at all.
  \item \textbf{Design intent is only as fine-grained as the source reports
        it.} A design change made without creating a named version is not
        visible until a version is cut or reconciliation polls the file.
  \item \textbf{Several claims are designed but not yet measured.} The
        human-intervention metrics, the comments-stripped ablation, the
        scalability benchmark and four of the five validation layers are
        specified and not yet run. Chapter~8 states which results exist and
        which do not.
  \item \textbf{Live provider behavior remains an integration-test
        dependency.} The adapter and webhook paths are implemented and
        documented, but the repository history does not yet contain a
        reproducible run against all three external provider accounts.
  \item \textbf{The local-inference hardware question remains unresolved.}
        No reproducible latency and memory measurement is committed yet, so
        the final model choice and any interactive-latency claim are deferred.
\end{itemize}
