\chapter{Testing and Early Validation}
\label{ch:testing}

Testing at this stage has two jobs: prove that what claims to be implemented
actually builds and behaves, and prove that the evaluation data which later
stages will be measured against is itself sound. Both now have real evidence
behind them. The verification pipeline, the deterministic linker, the change
analyser and the ingestion logic are each covered by automated tests, several of
them against the project's real database schema; the dataset pilot has been
double-annotated, adjudicated and given to external reviewers. What is still
missing is a run of the whole system against live GitHub, Jira and Figma
sources, and that limit is stated wherever it applies.

% ---------------------------------------------------------------------------
\section{Testing Strategy}
\label{sec:test-strategy}

The strategy follows the five-layer validation plan recorded in Chapter~3, but
only the layers that can honestly be exercised now are reported:

\begin{enumerate}
  \item \textbf{Static correctness} of the front end: the compiler and the linter
        are the cheapest tests that exist, they run on every change, and they
        enforce the domain vocabulary (a fifth verdict value, or a status with no
        label mapping, is a compile error rather than a run-time surprise).
  \item \textbf{Build reproducibility}: a production build must complete and
        pre-render every route, because a demo depends on it and because a
        broken route fails here rather than on stage.
  \item \textbf{Component and integration tests}: \texttt{vitest} suites for
        the shared contracts (including the ingestion engine, the rule records
        and the verdict gate) in \texttt{packages/\allowbreak{}contracts}, and
        for the worker in \texttt{apps/\allowbreak{}worker}: the packet builder,
        the bounded verifier loop and the gate end to end, deterministic
        linking, and the change analyser. The linking and publishing tests run
        against a real PostgreSQL engine (PGlite, in-process) loaded with the
        project's own migrations, and the analyser tests run against real git
        repositories, so neither the database constraints nor git behaviour are
        mocked away.
  \item \textbf{Evaluation against the pilot cases}: the change analyser is
        scored on all 15 pilot cases from the committed case files (FR-06).
  \item \textbf{Data validation}: automated integrity checks over every dataset
        case (schema, commit resolution, patch application, span bounds, test
        logs, leak and secret scans).
  \item \textbf{Annotation quality}: independent double labelling with raw
        agreement and Cohen's kappa reported against a pre-declared
        threshold~\cite{cohen1960}, followed by an external review in which
        industry engineers labelled the same cases and agreement was measured
        with Krippendorff's alpha. The two results are reported separately
        (Sections~\ref{sec:agreement} and~\ref{sec:external-agreement}).
\end{enumerate}

Two layers of the plan are declared but not yet runnable, and are listed as
such rather than implied: system-level acceptance tests against live GitHub,
Jira and Figma sources (the adapters are not connected yet), and comparative
baselines with a real local model (the pipeline currently runs with a
deterministic stub model).

\paragraph{Front end.} The typecheck and lint were re-run on 11 October on the
current code, after the mock data was removed and the reviewer screens were
wired to the database, and both pass. The production build also succeeds: 23 routes, 18 pre-rendered and 5 server-rendered, the conflict and link screens among the latter because they now read from Supabase instead of committed mock files. The \texttt{url.parse()}
deprecation warning recorded earlier as D-05 did not appear in this run.

\paragraph{Dataset.} The integrity report committed at
\texttt{docs/\allowbreak{}dataset/\allowbreak{}08\_\allowbreak{}integrity\_\allowbreak{}report.\allowbreak{}md} records 15 cases checked, 138
checks run, 0 failures, with per-case results of PASS and the check list stated
in the file. Two classes of check are explicitly \emph{not} run yet, and the
report says so: cross-split duplicate detection (no split is frozen) and a
checksum manifest of frozen cases (cases are not frozen). Reporting what the
test does not cover is part of the result.

\paragraph{Proof of concept.} The single remaining Python test module does not
collect. This is a genuine failure, not a formatting issue: the file imports
from a package that has not been laid out in the tree, and the modules it
depends on were removed from the repository. It is discussed as the edge case

\paragraph{Verification pipeline.} Abdullah's worker tests run the packet
builder, the bounded verifier loop and the gate end to end with a deterministic

of returning a clean result. These tests use the stub model; no real local
model has been evaluated yet.

\paragraph{Contracts and ingestion.} The shared contracts suite passes 115 of
115 tests, including Haaniah's ingestion engine with a mock vendor: a
redelivered event changes nothing, out-of-order deliveries converge, a missed
delivery is reconciled as a system event, and an outage marks checkpoints stale
(TC-21). The engine is not yet connected to live sources. The contracts
typecheck reports 6 errors in one test file (TC-09); the tests themselves pass.

\paragraph{Linking.} The 16 linking tests pass against the same migrations as
the hosted Supabase project, covering the normal, no-key, unknown-key and
duplicate-delivery cases used in the demonstration (TC-10 to TC-15). An earlier
version of the linker named an index condition that did not match migration
00010, and these tests caught it. With migration 00015 applied to the hosted
project, \texttt{npm run demo:\allowbreak{}linking -- -{}-live} played the same
five events through \texttt{supabase-js} on 11 October and produced the same
outcomes as the local run. No real GitHub webhook has been fed through it yet

\paragraph{Change analyser.} On the 15 pilot cases the analyser reported every

symbol (11/11) and flagged none of the unchanged ones (21/21, hard negatives
included), in a median of 0.3\,s per case (TC-17). The one miss is a key inside

reaches the verifier's input: run through the production evidence provider and
packet builder, it fills the diff-hunk, symbol-card and test-evidence slots of

\paragraph{Agreement.} Both annotation sheets are complete. Verdict agreement

without a re-run. All seven disagreements were adjudicated, and two of them led to
rules being added to the annotation manual (Section~\ref{sec:agreement}).

\paragraph{External review.} Ten industry engineers labelled the same 15 cases,

0.08--0.80, too wide at this sample size to say whether the gate is met

internal result and does not replace it.

\section{Dataset Pilot Agreement}
\label{sec:agreement}

\paragraph{Protocol.} The pilot is 15 cases drawn from 3 TypeScript/React
repositories, covering all four verdicts with same-module hard negatives. Two
members label every case independently in their own sheet and may not discuss
cases until both sheets are submitted; the third member adjudicates each
disagreement into \texttt{06\_\allowbreak{}adjudication\_\allowbreak{}log.\allowbreak{}csv} without editing the
original sheets. The pre-declared gate is Cohen's $\kappa \geq 0.70$ on the
verdict field~\cite{cohen1960}; if it is not met, the annotation manual is
rewritten from the disagreements and the pilot is re-run, which the protocol
states in advance is an expected outcome rather than a failure.

\paragraph{Current state.} Both sheets are complete. Haaniah's sheet
(\texttt{annotator\_\allowbreak{}B\_\allowbreak{}haaniah.\allowbreak{}csv}) was committed in \texttt{8657955} and
Abdullah's (\texttt{annotator\_\allowbreak{}A\_\allowbreak{}abdullah.\allowbreak{}csv}) in \texttt{bfb3201}. Each of the
15 rows carries a verdict, freshness state, review flag, reason code, evidence
span identifiers, a written justification and a time estimate. Neither annotator
constructed the cases. The constructor (Mishal) did not label them and acted as
adjudicator, and the constructor's answer key is kept out of the repository.

\paragraph{Result.} Running the agreement script over the two sheets gives:

\begin{verbatim}
$ python3 docs/dataset/tools/agreement.py \
    docs/dataset/05_raw_annotations/annotator_A_abdullah.csv \
    docs/dataset/05_raw_annotations/annotator_B_haaniah.csv
Cases labelled by both annotators: 15
| Field           | Raw agreement | Cohen's kappa |
| verdict         | 0.93          | 0.90          |
| freshness_state | 1.00          | 1.00          |
| review_required | 1.00          | 1.00          |
Evidence spans: mean Jaccard (IoU) = 0.83; exact match = 9/15
\end{verbatim}

The two annotators chose the same verdict on 14 of 15 cases and the same
freshness state and review flag on all 15. The verdict gate is met. Span
agreement is lower (mean IoU 0.83, 9 of 15 exact). In every span disagreement the
annotators agreed on the verdict and differed only on which supporting code to
cite, so the main weakness of the manual was span selection rather than verdicts.
The result was computed twice, once by each of two team members, with the same
values.

\paragraph{Adjudication.} The script listed seven disagreements: one verdict and
six span sets. Each was resolved in \texttt{06\_\allowbreak{}adjudication\_\allowbreak{}log.\allowbreak{}csv}, recording
both original labels, the decision, the evidence used and any rule added. The
original sheets were not edited.
\begin{itemize}
  \item \textbf{P10 (verdict).} SUPPORTED vs.\ INSUFFICIENT\_EVIDENCE for a toast
        timer fix that has no test. Resolved as INSUFFICIENT\_EVIDENCE with
        reason MISSING\_TEST: the manual already says that unexercised runtime
        or timing behaviour must not be labelled SUPPORTED. The SUPPORTED
        argument was reasonable, which shows the rule needed to be stated more
        plainly. This became rule R1.
  \item \textbf{P03 and P05 (spans).} The annotators split on whether an
        unchanged function on the path that delivers the observed value counts
        as relevant evidence. It now does, under rule R2.
  \item \textbf{P02, P07, P10, P11 (spans).} Each was resolved by checking which
        candidate span lies on the code path the criterion describes.
\end{itemize}
The adjudication also found an error in the construction itself. In P11 both
annotators, independently, cited a span that the constructor's key had marked as
a hard negative. On inspection they were right: that function is where the
retained trail is stored. The key was corrected. Blind double annotation is meant
to catch exactly this kind of error, and here it did. With R1 and R2 added, the
annotation manual is frozen as version~1.

\paragraph{Limits of this result.} Fifteen cases is a pilot. With this few items
a single changed label would move $\kappa$ noticeably, so 0.90 shows that the
manual is usable, not that the oracle is validated. Both annotators are project
members, and the supervisor audit of a sample of cases, required by the dataset
protocol, is still pending. The external review in the next section was run to
test the first of these limits.

\section{External Review Agreement}
\label{sec:external-agreement}

\paragraph{Summary.} Ten industry engineers labelled the 15 cases, two per case,
as a pilot of the review instrument. On the cases where the evidence is
decisive, they agreed with the adjudicated labels on 19 of 22 judgements.
Overall verdict agreement was $\alpha = 0.48$ (95\% CI 0.08--0.80). With two
labels per case, the interval is too wide to say whether external agreement
meets the 0.70 gate, so the result is inconclusive rather than a pass or a
fail. None of the reviewers used the abstention label. Since the gold labels
come from trained annotators with adjudication, we treat this as a finding
about the short web guide, and the review will be re-run with a revised page
and more reviewers per case before the final evaluation.

\paragraph{Why.} The internal result above has one obvious weakness: both
annotators belong to the project team, wrote or read its documents, and might
share its conventions without knowing it. To test that, the same 15 cases were
given to engineers outside the project.

\paragraph{Protocol.} Reviewers used a public web
page\footnote{\texttt{https://mishalfatima09.github.io/unify-review/}} that shows each case's
requirement, the code change, the candidate evidence spans, the test results
and the source events, all on one screen. The cases are split into five fixed
batches of three, and each reviewer labels one batch. Two reviewers were
assigned to each batch, so every case received exactly two external labels. The
page carries a two-minute guide: the four verdict definitions and four rules
condensed from manual v1, including R1 (runtime claims need a test) and the
PARTIAL rule (version \texttt{v1-web-b3}). Reviewers saw no internal
labels. Each reviewer downloaded a CSV in the same format as the internal sheets
and returned it. Three properties of the page matter when reading the results:
\texttt{review\_required} is not asked but derived from the verdict and the
freshness answer, so it is not reported as an agreement field; the freshness
question starts preset to ``current''; and marking evidence spans is
optional.

\paragraph{Panel.} Ten engineers took part: five software engineers or
software development engineers, two senior engineers, two in quality assurance
and one forward-deployed engineer. Nine reported their experience: median 3
years, range 2 to 6. The page records only time while a case is on screen,
rounded to whole minutes with a minimum of one per case. On that measure the
median reviewer spent 5.5 minutes on their three cases (range 3 to 19). In the
report reviewers are identified by the random reviewer id the page assigns, not
by name.

\paragraph{Method.} Because each case was labelled by a different pair of
people, Cohen's kappa does not apply. Krippendorff's alpha (nominal) allows any
set of raters per item and is used instead~\cite{krippendorff2018}. A bootstrap
over cases (5{,}000 resamples) gives the interval. Each external label is also
compared with the \emph{adjudicated reference}: the two internal annotators'
agreed label, or the adjudicated label where they disagreed. The reference uses
only committed files. The constructor's answer key is not read. For comparison,
the internal pair's alpha is computed with the same function.

\begin{verbatim}
$ python3 docs/dataset/tools/agreement_multi.py docs/dataset \
    <ten external CSV files>
External reviewers: 10; labelled rows: 30; cases covered: 15/15
| Field           | Ext. alpha | 95% CI        | Int. alpha (A,B) |
| verdict         | 0.48       | [0.08, 0.80]  | 0.91             |
| freshness_state | -0.07      | [-0.21, 0.00] | 1.00             |
Cases where both external reviewers chose the same verdict: 10/15
External rows matching the reference: verdict 19/30, freshness 25/30
Verdict confusion (rows = reference, columns = external)
        SUP  CON  PAR  INS
  SUP    11    0    1    0
  CON     1    6    1    0
  PAR     0    0    2    0
  INS     3    1    4    0
Evidence spans: 18/30 rows marked spans; mean IoU 0.78; exact 11/18
\end{verbatim}

\paragraph{Reading the result.} The interval is the important number. With
15 cases and two labels each, a single changed label moves alpha visibly, so
0.48 is an estimate with a range of 0.08 to 0.80 around it, not a measured
failure. The script was checked against the \texttt{krippendorff} Python
package, which gives the same values to three decimals.

Where the reference label is SUPPORTED, CONTRADICTED or PARTIAL (eleven cases),
the external engineers matched it on 19 of 22 judgements, and each of the three
misses (P01, P04, P09) is one reviewer against a second who matched. The
remaining disagreement sits on the four cases whose reference is
INSUFFICIENT\_EVIDENCE: no reviewer used that label, choosing PARTIAL,
SUPPORTED or CONTRADICTED instead. These are the cases governed by the
manual's abstention rules (an untested runtime claim, a requirement edited
after the merge). The page stated those rules in a two-minute guide, whereas
the internal annotators worked from the full manual; with most time on case
screens under two minutes, the guide is the likeliest place for the gap. The
freshness alpha is reported but not interpreted: 25 of 30 answers were
``current'', which is also the page's default, and alpha is not informative
when one category dominates like this.

\paragraph{What changes before the final evaluation.} The review page will
give each abstention rule a worked example and ask for the reason before the
verdict, the freshness question will have no default, a written justification
will be required, and each case will get at least three reviewers so the
interval narrows. No case enters the frozen gold set before that re-run and the
supervisor audit (D-08).

\section{Edge and Failure Cases}
\label{sec:edge-cases}

\paragraph{Observed failure: the orphaned proof-of-concept module.}
\emph{Input.} \texttt{python3 -m pytest tests/\allowbreak{}} from \texttt{unify\_poc/}.
\emph{Why it matters.} The evaluation walkthrough will open the repository and
run something. A test directory that cannot collect is worse than no test
directory, because it implies coverage that does not exist, and it is exactly
the kind of gap the worksheet asks to be discussed rather than hidden.
\emph{Observed behaviour.} Collection aborts with
\texttt{ModuleNotFoundError: No module named 'unify'}; inspecting further, the
package directory in the tree holds a single module whose own imports
(\texttt{from .\allowbreak{}adapter import Adapter}, \texttt{from .\allowbreak{}normalizer import
FIGMA\_\allowbreak{}RE}) reference files deleted by the \texttt{066ef56} ``start fresh''
commit. \emph{Interpretation.} This establishes only that the surviving files
are not runnable; it says nothing about the quality of the code they contain,
and it does not affect the front end. \emph{Corrective action.} D-01: either
restore the two modules from history and make the test pass, or remove the
orphan before the evaluation tag. Owner: Abdullah. This is a decision to be
taken, not a fix that has been applied.

\paragraph{Executable demo cases: deterministic linking.}
The linking demonstration (\texttt{npm run demo:\allowbreak{}linking} in
\texttt{apps/\allowbreak{}worker}) plays five pull-request events through the real
linker against the project's schema and prints each outcome and the resulting
\texttt{edges} table. Each case is also an automated test (TC-11 to TC-15):
\begin{itemize}
  \item \emph{Normal.} \texttt{UNI-123} in the title, branch and a commit: one
        \texttt{TRACKS} edge. The three places are recorded as provenance.
  \item \emph{Edge: no key.} The event is still recorded, because the
        \texttt{events} table is a log, but no edge is written.
  \item \emph{Failure: unknown key.} \texttt{UNI-999} has no ticket. The
        linker reports it and does not create a placeholder ticket. An edge to
        an invented node would be evidence the system does not have. The same
        title contains \texttt{UTF-8}, which the project allow-list rejects.
  \item \emph{Edge: same delivery twice.} The second insert hits
        \texttt{UNIQUE (source\_tool,} \texttt{vendor\_\allowbreak{}delivery\_\allowbreak{}id)} and returns no row.
        The linker treats that as ``already processed'' and writes nothing.
        Because the check and the insert are one statement, two concurrent
        redeliveries cannot both pass.
  \item \emph{Edge: new event, same link.} A later edit to the same pull
        request names \texttt{UNI-123} again. The partial unique index from
        migration 00010 keeps one current edge per pair and type. A link a
        reviewer has dismissed is not revived; one that was revoked can be
        created afresh.
\end{itemize}
After all five events the \texttt{edges} table holds one row and
\texttt{events} holds four.

\paragraph{Failure case for the demo: fabricated citation (T10).}
The scenario matrix in Chapter~4 assigns T10 as the demonstration's failure
case: a fabricated citation injected into a verdict must be downgraded by the
gate and must never reach the reviewer as a decisive status. It now runs end to
end through the packet builder, the verifier loop and the gate
(\texttt{npx vitest run test/\allowbreak{}e2e-\allowbreak{}gate.\allowbreak{}test.\allowbreak{}ts -t T10}
in \texttt{apps/\allowbreak{}worker}). A verdict citing one real and one invented
span keeps the real one and is downgraded; a verdict whose only citations are
invented is never stored as decisive (TC-20). The run uses the deterministic
stub model; with a real model the gate is the same code.

\paragraph{Edge cases in change analysis.}
Two kinds of change have no function to attach to, and the analyser reports
them as such rather than forcing a match. In pilot P06 the change is a pair of
re-export lines and a build configuration: the analyser lists them as
module-level changes and finds no changed symbol, which is correct. Code whose
target cannot be known statically, such as \texttt{import(variable)} or
\texttt{handlers[type]()}, is listed as unresolved inside the changed symbol and
never turned into a link, so a guessed relation cannot reach the verifier as
evidence.
