\chapter{Software Requirements}
\label{ch:requirements}

This chapter states what UNIFY must do and how each requirement will be
checked. The requirements are written around one decision: whether a single
proposed code change (one pull request) is adequately supported by the intent
it claims to implement. Everything below either feeds that decision, protects
its evidence, or routes its outcome to the right person.

Since the proposal defence, three groups of requirements have been added in
response to the panel: requirement-to-code traceability
(FR-22 to FR-24), code comments as semantic evidence with a repository quality
gate (FR-25 to FR-27), and a reduced role for the product manager in the
confirmation and configuration loops (FR-28, FR-29). These are marked as new in
the tables.

GitHub, Jira and Figma are read-only sources: UNIFY receives their events and
polls them to fill gaps, but never writes back. Slack is a delivery channel
only. A Slack message is never used as evidence for a verdict.

\paragraph{Reducing PM involvement.}
The panel asked us to take the PM out of routine loops. The use cases separate
three loops in which a human used to be involved:
\begin{itemize}
  \item \textbf{Configuration.} The system derives the workflow state map and a
        default grace period from the project's own history; the PM
        \emph{approves} the proposal rather than writing it (FR-29).
  \item \textbf{Confirmation.} Links above an upper confidence threshold are
        confirmed automatically and remain reversible; links inside the
        uncertain band are sent to the code owner or assignee, not the PM; links
        below the band are kept as silent suggestions (FR-28).
  \item \textbf{Resolution.} Acknowledging or resolving a finding stays a human
        judgement, made cheaper through grouping and bulk actions (FR-18).
\end{itemize}

\paragraph{Scope limit on repository quality.}
UNIFY relies on the meaning that developers put into names, comments and
directory structure. It therefore targets repositories with reasonable
documentation and conventional layout. This is a stated limitation rather than
a hidden assumption: each repository is scored when it is connected (FR-27),
and a deliberately low-documentation group of repositories is evaluated
separately so the drop in quality is measured, not asserted.

\paragraph{Language scope.}
UNIFY supports two language families: Python, and TypeScript/JavaScript
(including React front-end code). The code analyser, symbol cards, indexing and
retrieval cover both, for repositories up to roughly 500k lines of code. Other
languages, and larger repositories, are future work. This follows proposal
§27.3, which supersedes the TypeScript-only scope of §7.2. Evaluation results
are reported separately for each language family rather than blended into one
score; the current pilot dataset covers TypeScript/React repositories, and
Python repositories will be screened against the same eligibility gate.

\usecase{UC-01 \quad Verify a change against its linked intent}
  {Code reviewer (primary); developer.}
  {A pull request is opened or updated, or the reviewer selects it.}
  {The repository is connected; the PR is linked to at least one Jira ticket
   with acceptance criteria.}
  {(1) The reviewer selects the PR and its base/head commits.
   (2) The system lists each atomic criterion from the linked ticket and any
   approved design constraints.
   (3) For each criterion it builds a bounded evidence packet and runs the local
   verifier.
   (4) The reviewer sees one evidence case per criterion: status, cited code and
   test spans, reason and missing evidence.}
  {If a linked source is stale, affected criteria show \texttt{SOURCE\_STALE}
   instead of a verdict. If the model server is unavailable, deterministic rules
   still run and verification is shown as unavailable. A verdict whose
   citations do not resolve is downgraded to \texttt{INSUFFICIENT\_EVIDENCE}.}
  {Every decisive status is backed by citations the reviewer can open.}
  {FR-06 to FR-11, FR-16, FR-17.}

\usecase{UC-02 \quad Confirm or reject a cross-tool link}
  {Code owner or assignee; reviewer.}
  {The system infers a link whose confidence falls inside the uncertain band.}
  {The link is not explicit (no ticket key or design URL in the PR).}
  {(1) The system notifies the owner of the affected code.
   (2) The owner sees both artifacts and the evidence for the link.
   (3) The owner confirms or rejects it; the decision, actor and reason are
   recorded.}
  {Above the upper threshold the link is confirmed automatically with
   \emph{system-confirmed} provenance and can be reversed later. Below the band
   it stays a silent suggestion.}
  {Only confirmed or deterministic links can produce a decisive finding.}
  {FR-04, FR-05, FR-28.}

\usecase{UC-03 \quad Resolve or dispute a finding}
  {Reviewer, developer, designer or PM, depending on the finding.}
  {A finding is raised by a rule or a gated verdict and routed to the user.}
  {The finding is open.}
  {(1) The user opens the finding and its evidence.
   (2) The user acknowledges, resolves, suppresses (with a reason and expiry)
   or reopens it.
   (3) The transition is written to the audit log with the actor, reason and an
   evidence snapshot.}
  {The user disputes the verdict. The correction is stored as a labelled
   example for the next adaptation round, kept out of the current test split.}
  {The finding's state and full history are recoverable later.}
  {FR-15, FR-18, FR-20.}

\usecase{UC-04 \quad Review a requirement--code divergence (P4)}
  {Developer; PM.}
  {A requirement changes while its anchored code does not, or anchored code
   changes with no matching requirement or ticket change, beyond the grace
   period.}
  {The requirement has a confirmed anchor; the change is not formatting-only or
   in a generated file.}
  {(1) The system raises a divergence finding showing both sides of the anchor.
   (2) The developer updates the code or the PM updates the requirement.
   (3) The finding is resolved through UC-03.}
  {If re-anchoring fails, the anchor is marked broken and the user is told,
   rather than the old lines being kept silently.}
  {Requirements and the code that implements them do not drift apart unnoticed.}
  {FR-22, FR-23, FR-24.}

\usecase{UC-05 \quad Approve a pre-filled workflow configuration}
  {Product owner / PM.}
  {A project is connected, or enough new history has accumulated to update the
   proposal.}
  {Jira workflow transitions and merge history are available.}
  {(1) The system derives the canonical state map from observed transitions
   and proposes a grace period from the observed merge-to-done delay.
   (2) The PM reviews a preview of which findings the configuration would
   produce.
   (3) The PM approves or edits it; the result is stored as a new rule version.}
  {The PM rejects the proposal and keeps the current version.}
  {Rules run against a configuration the PM approved but did not have to write.}
  {FR-19, FR-29.}

\usecase{UC-06 \quad Connect a repository and view its eligibility score}
  {Product owner / PM; reviewer.}
  {A new repository is connected.}
  {Read-only access to the repository has been granted.}
  {(1) The system profiles comment and docstring coverage, identifier quality,
   directory conventions, documentation files and tests.
   (2) It shows the score against the published threshold.
   (3) The repository is admitted and indexing starts.}
  {Below the threshold, the repository is admitted only after an explicit
   warning that link quality is not guaranteed.}
  {Users know in advance how reliable UNIFY's links will be for this codebase.}
  {FR-25, FR-27.}

\section{Non-Functional Requirements}
\label{sec:nfr}

Each non-functional requirement has a measurable target. Targets marked
\emph{provisional} are frozen after the technical spike.

\subsection{Reliability}
\begin{itemize}
  \item \textbf{NFR-01 Idempotency and convergence.} Duplicate delivery
        produces zero duplicate findings; out-of-order delivery reaches the same
        final state as ordered delivery in 100\% of controlled tests.
  \item \textbf{NFR-02 Outage tolerance.} Ingestion survives a defined period of
        vendor downtime without losing events, using the queue plus checkpoint
        reconciliation.
  \item \textbf{NFR-03 Incremental correctness.} Incremental and full-rescan
        findings agree in at least 99\% of benchmark cases.
  \item \textbf{NFR-04 Graceful degradation.} With the model server down,
        ingestion and Rules 1--3 keep working and verification is reported as
        unavailable, never silently skipped.
\end{itemize}

\subsection{Usability}
\begin{itemize}
  \item \textbf{NFR-05} A participant in the PM role completes the acceptance
        task without help from a developer.
  \item \textbf{NFR-06} PM-directed prompts per finding are reported separately
        from developer- and designer-directed prompts, and human interventions
        per 100 ingested events are reported against an all-manual baseline.
\end{itemize}

\subsection{Performance}
\begin{itemize}
  \item \textbf{NFR-07} p95 analysis time for one pull request is under 60
        seconds on the declared hardware and repository class
        (\emph{provisional}).
  \item \textbf{NFR-08} The system runs within one Docker Compose deployment on a
        single host, including the local model server.
\end{itemize}

\subsection{Security}
\begin{itemize}
  \item \textbf{NFR-09} GitHub, Jira and Figma access uses read-only,
        least\-privilege scopes; OAuth tokens are encrypted at rest and held only
        by the API service.
  \item \textbf{NFR-10} Ticket, design and code text is treated as untrusted
        input: the output schema is enforced and instructions found inside
        artifacts are never followed or executed.
\end{itemize}

\subsection{Privacy, Grounding and Reproducibility}
\begin{itemize}
  \item \textbf{NFR-11 Locality.} No repository, ticket or design content leaves
        the deployment boundary, checked by egress inspection during testing.
  \item \textbf{NFR-12 Grounding.} 100\% of \texttt{SUPPORTED} and
        \texttt{CONTRADICTED} findings carry valid provenance; unsupported
        confident assertions stay at or below 2\% on the gold test set.
  \item \textbf{NFR-13 Abstention.} At least 80\% correct abstention on
        labelled ambiguous cases.
  \item \textbf{NFR-14 Reproducibility.} The same packet with the same pinned
        model and settings gives the same verdict class across runs.
\end{itemize}
